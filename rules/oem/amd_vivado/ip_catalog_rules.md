# AMD/Xilinx IP catalog rules (Vivado)

## Locking and versioning

- An IP instance generated via the IP catalog (`create_ip`) is versioned; a project's `.xci` records
  the exact IP version and its parameter set. Upgrading the installed Vivado/IP-catalog version does
  NOT retroactively upgrade an already-generated `.xci` — `report_ip_status` flags IP that is
  out-of-date relative to the currently-installed catalog, and `upgrade_ip` must be run explicitly.
  An out-of-date IP is not an error by default; it will still synthesize against its originally
  generated version unless upgraded.
- `LOCK_LEVEL` (or the "Lock" checkbox in the IP customization GUI) freezes the IP's underlying
  netlist/output so `upgrade_ip`/regeneration will not touch it — appropriate for a signed-off IP
  configuration a team does not want silently regenerated by someone else's Vivado version, but also
  means a real upstream fix (e.g. an updated core release fixing a known erratum) will not reach a
  locked instance until it's explicitly unlocked and regenerated.

## Out-of-context (OOC) vs. global synthesis

- An IP synthesized `OOC` (the catalog default for most IP) builds its own checkpoint independently
  of the top-level synthesis run, with its own default clock/timing assumptions unless the project
  supplies IP-specific constraints. A change to the IP's parameters requires regenerating the IP
  (and its OOC run) — editing generated IP output files directly is not a supported/durable path
  and will be overwritten on the next regeneration.

## Managed IP vs. hand-integrated netlist

- A `.xci`-driven IP re-generates its output products (`.veo`/simulation models/example designs) from
  its parameter set each time `generate_target` runs; treat the generated Verilog/VHDL wrapper as
  disposable, not something to hand-edit. If a specific behavior needs changing beyond what the
  IP's own GUI parameters expose, that is a signal to wrap the IP in a small hand-written adapter
  module rather than editing generated IP sources.

## Checkpoints (`.dcp`)

- A design checkpoint captures netlist + constraints + (if post-place/route) placement/routing at
  one specific point in the flow. `read_checkpoint`-ing a `.dcp` from a different part or a
  materially different constraint set than the current project targets can silently succeed while
  producing a design that doesn't match what's expected — confirm the checkpoint's originating part/
  run before trusting it as a drop-in starting point for further implementation.
